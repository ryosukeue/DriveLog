# 移動継続判定 改善メモ

- 状態: 主要ロジック実装済み（診断件数の永続化は未実装）
- 作成日: 2026-08-10
- 対象: 位置情報の観測間隔が15分以上空いた場合の移動区間判定

## 背景

現在は、連続する位置情報の間隔が15分以上空くと、移動中かどうかに関係なく別の移動区間へ分割している。

DriveLogの通常記録は大幅位置変更サービス（Significant Location Change）を中心としているため、実際には走行を継続していても位置情報の更新が15分以上空く場合がある。このとき区間が細かく分断され、分断後の区間が「2点以上・100m以上」の採用条件を満たさず、ポリラインや移動距離が消える可能性がある。

## 改善方針

15分を一律の分割条件にはせず、**15分以上空いても、移動継続の根拠があれば同じ移動として接続する**。

一方、根拠が弱い区間まで接続すると、滞在地点をまたいだ直線や、別々の移動を一本の経路として表示する問題が起きる。そのため、15分から90分までを「継続判定が必要な空白」として扱い、移動・滞在・距離・速度の情報を組み合わせて判定する。

### 時間による基本区分

| 観測間隔 | 扱い |
| --- | --- |
| 15分未満 | 現在の通常判定を使用する |
| 15分以上90分未満 | 移動継続の根拠を評価し、根拠があれば接続する |
| 90分以上 | 原則として別の移動に分割する |

90分は絶対上限として残す。長時間の空白を無条件に接続して、実際には記録できていない経路を大きな直線で補うことを防ぐためである。

## 15分以上の空白を接続する条件

15分以上90分未満の空白では、最初に「接続してはいけない根拠」を確認し、その後に「移動が続いていた根拠」を評価する。

### 必ず分割する条件

次のいずれかに該当する場合は、移動継続の根拠があっても分割する。

1. 日付が変わっている
2. 観測間隔が90分以上ある
3. 空白時間内に確定した滞在または `CLVisit` がある
4. 2地点を接続した場合の推定速度が、既存の異常移動判定（250km/h超）に該当する
5. 位置情報が既存の品質判定で異常値として除外されている

### 接続に使う根拠

必ず分割する条件に該当しない場合、次の情報を使用する。

- 空白の前後、または空白時間内に自動車移動のモーション情報がある
- 空白の前後で同じ移動種別が継続している
- 2地点間が100m以上離れ、平均移動速度が0.5km/h以上250km/h以下である
- 空白時間内に静止、滞在、移動終了を示す情報がない

初期実装では、次のどちらかを満たす場合に接続する。

1. 自動車などの移動モーションが空白をまたいで確認できる
2. モーション情報が不足していても、前後地点から計算した距離と平均速度が現実的で、滞在を示す根拠がない

Bluetooth接続中の車両情報も継続根拠として利用できるが、最初の実装では位置・モーション・滞在判定のみで成立させる。車両判定と移動区間判定を強く結合すると、Bluetoothの切断や車種未登録によって経路自体が消える可能性があるため、Bluetoothは後から追加できる補助根拠として扱う。

## 判定イメージ

```text
日付が変わった                    -> 分割
観測間隔が90分以上                -> 分割
確定した滞在・CLVisitがある        -> 分割
接続時の推定速度が250km/hを超える  -> 分割または異常点を除外
観測間隔が15分未満                -> 通常判定
移動モーションが空白をまたぐ       -> 接続
距離・平均速度が現実的で滞在なし    -> 接続
上記の根拠がない                  -> 分割
```

## 実装案

### 設定値

`SegmentationRules` に、用途が分かる設定値を追加する。

```swift
softContinuousGap: 15 * 60
absoluteMaximumContinuousGap: 90 * 60
minimumBridgeDistance: 100
minimumBridgeAverageSpeed: 0.5 / 3.6
maximumBridgeAverageSpeed: 250 / 3.6
```

単位は時間が秒、距離がメートル、速度がメートル毎秒とする。

現在の `maximumContinuousGap` は15分で即分割する意味になっているため、ソフト上限と絶対上限に分ける。名称だけで判定の意図が分かるようにする。

### 判定処理

`MovementSegmenter` の先頭で15分を即時返却している処理を、独立した継続判定へ置き換える。

候補名:

```swift
MovementContinuityEvaluator
```

入力は前後の位置情報、観測間隔、滞在情報、モーション情報、設定値とし、次のいずれかを返す。

```swift
case continuous(reason: ContinuityReason)
case split(reason: BoundaryReason)
```

判定理由も返すことで、処理結果の検証とログ集計を可能にする。同じ入力から常に同じ結果になる純粋な判定処理として実装する。

### 再処理

判定ロジックを実装するときは `ProcessingAlgorithmMigrator.currentVersion` を7から8へ上げ、保存済みの派生データを新しい条件で再計算する。生の位置情報は変更しない。

## 診断ログ

座標や端末識別子を記録せず、次の件数だけを集計できるようにする。

- 15分以上90分未満の空白を評価した件数
- モーション根拠で接続した件数
- 距離・速度根拠で接続した件数
- 滞在根拠で分割した件数
- 90分上限で分割した件数
- 異常速度で分割または除外した件数
- 分割後に採用条件未満となり破棄された区間数

これにより、ポリラインが消えた原因が「取得できなかった」のか「分割された」のか「短い区間として破棄された」のかを切り分けられる。

## 確認ケース

| ケース | 期待結果 |
| --- | --- |
| 16分空き、2km移動、自動車モーションあり | 接続 |
| 45分空き、30km移動、自動車モーションあり | 接続 |
| 20分空き、モーション情報なし、現実的な距離と速度、滞在なし | 接続 |
| 16分空き、移動距離10m、確定した滞在あり | 分割 |
| 20分空き、接続時の推定速度が250km/h超 | 分割または異常点を除外 |
| 90分以上空く | 分割 |
| 日付をまたぐ | 分割 |
| 空白前後の区間がそれぞれ採用条件未満になる | 有効な移動が消えないか確認 |

実機確認では、位置情報の時刻、空白時間、分割理由、描画されたポリライン、算出距離を同じ記録について比較する。

## 導入手順

1. 継続判定を独立した処理として追加する
2. 15分の即時分割を新しい判定へ置き換える
3. 判定理由別の診断件数を追加する
4. アルゴリズムバージョンを8へ上げて再処理する
5. 実機ログで誤接続と経路消失の両方を確認する
6. 必要なら閾値を調整する
7. 実装確定後に `docs/processing-rules.md` の90分・15分に関する記述を新仕様へ更新する

## 完了条件

- 15分以上90分未満空いても、移動継続の根拠がある経路は同一区間として残る
- 確定した滞在、日付変更、90分以上の空白、異常な位置ジャンプは接続しない
- 同じ入力では常に同じ判定結果になる
- 分割・接続の理由を座標なしで診断できる
- 再処理後も生の位置情報は保持される
- 実装後の正式仕様とドキュメントが一致する
